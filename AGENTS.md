# Architecture rules

- Keep business storage operations bucket-aware through the provider port; pass original object keys, never generated public URLs, so private and multi-bucket files remain addressable.
- Orchestrate document file cleanup in DocumentService, retain the row when file deletion fails, and roll back newly uploaded files on failed persistence; this prevents silent orphan creation on the normal CRUD paths.
- Normalize campaign scheduling in the application service and persist it through the domain entity; editing and dedicated scheduling must agree.
- Ship the frontend container from the production dist artifact with SPA fallback and JavaScript MIME for PDF workers; keep build inputs and private environment files out of the serving image.
- Mount validated public runtime configuration read-only before client initialization; operator self-hosted settings override persisted deployment profiles to prevent stale database settings from rerouting a release.
- Generic system settings and browser configuration must reject private credentials; server provider ports read secrets only from their execution environment.
- Release the frontend independently with an immutable image tag and explicit public config path; never rebuild or restart existing backend services during a frontend release.
- SMS uses the server-side provider port and reports accepted status separately from delivery; server role authorization protects paid sends.
- Self-hosted startup scripts must not generate, rewrite, or print environment secrets; apply application migrations explicitly rather than relying on nested initialization mounts.
- Communication actions must resolve user contacts through UserService and check provider results before claiming delivery; recipient IDs are not phone numbers or email addresses.
- Inspection updates must persist dates and inspector IDs and read back the stored entity; the inspection workflow policy lives in the inspections referential, not in presentation code.
- Supplier uploads must use DocumentService once with the supplier association; shared cleanup and rollback prevent duplicate files and unlinked records.
- ConsultantScopeService filters project-bound presentation records; server-side permissions remain authoritative and are not replaced by UI filtering.
- Payment initiation limits, approval chains, and deadlines come from the injectable payment-initiation referential; DTO compatibility exports must not own business rules.
- InspectionComplianceService evaluates phase evidence against the inspection-compliance referential; pending or rejected inspections must not count as completed compliance evidence.
- Keep GIS network features, structures, open domain/asset-type referentials and spatial analysis in the infra schema with opaque project UUIDs and structural-only constraints; business types are seeded data, never CHECK lists, so new networks need no schema change.
- Reuse GeocodingService for address resolution and a spatial-analysis port for metric PostGIS operations; geocoding approximations must not determine authoritative project coverage counts.
- Compose calendar data through ProjectWorkbenchService and its repository port, with server-authorized project selection; dated operational entries must stay distinct from payment aliases to prevent double counting.
- Keep privileged workbench access helpers in the unexposed workbench_private schema behind invoker API wrappers; never grant anonymous execution.
- Hydrate project-related collections into their declared entities or DTOs in the repository adapter before aggregation; raw database rows must never reach domain-to-DTO serializers.
- Reuse the existing task, phase, inspection, payment and BOQ services for workbench actions, retaining original entity IDs independently from dated calendar-event IDs to avoid duplicate business records.
- Compose workbench financial/resource summaries and planning previews through canonical financial, resource and metrics services plus existing Gantt/PERT views; projections must not create competing calculations or records.
- Store operation context rules in referential_items and evaluate them on the server; stable source identifiers, request keys and finalized-row protections prevent disconnected declarations and duplicate retries.
- Extend ProjectImportTemplateService for controlled mapped planning previews and pass prepared datasets to the existing importer; preserve and report unmapped source sections rather than inventing their interpretation.
- Read planning workbooks through a technical reader and review their configurable mappings in the existing project import; persist full source evidence in phase custom data and task provenance, and archive original files through DocumentService so narratives never become unreadable JSON descriptions.
- Enrich every BOQ ingestion source through MeterService and injectable metering policies; keep explicit source quantities and audited price corrections instead of silently replacing documentary evidence.
- UnifiedBoqParser owns document source routing, including technical PDF reader/OCR and reviewed dimensions; all inputs use MeterService and the same import dialog, with sources archived through DocumentService and no competing calculator or storage table.
- Manual BOQ lines use UnifiedBoqParser.fromManual and the existing assisted-line form; calculator access is line-scoped, never a separate workspace, so source quantities and metering provenance share the import pipeline.
- Route BOQ document hooks and quantity-calculator persistence through BoqDocumentService with an injectable repository port; lazy adapter resolution keeps provider dependencies out of presentation code.
- Run browser application tests through Vitest and release-script tests through Node's test runner; separate discovery avoids bundling Node built-ins into jsdom.
- Project detail owns one URL-driven tab navigation; phase and workbench BOQ views compose the existing DqeWorkspace, so opening a presentation never creates derived takeoff records.
